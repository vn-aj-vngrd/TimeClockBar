## Product finding

The app already provides useful access and awareness: native menu-bar presence, ticking state, embedded pages, global shortcut, persisted settings, and offline/polling indicators. What it lacks is a coherent workday workflow: next action, completion evidence, recovery from missed deadlines, and safe capture of report content.

Changing sounds alone cannot supply that workflow. The priority is to connect reminders to dated checkpoints and confirmed clock transitions, then introduce a native Today view and recoverable draft editor.

## Additional UX and engineering observations

- The installed popover gives much of its space to the remote navigation, time-clock panel, and overview/leave content. A native summary could surface the next checkpoint without scrolling through the website. The screenshot is evidence for this layout observation, not for new notification behavior.
- Settings devote multiple sections to sound selection and per-event switches. A schedule preview, actual next reminder, and release-build notification test would better explain whether reminders are ready. Existing test buttons are inside `#if DEBUG`.
- The DOM detector uses body-wide text and broad timer fallbacks, including “resume”, “login”, and “take break”. Visible or incidental text can therefore affect state classification. Capture sanitized live HTML fixtures before tightening selectors; the live DOM's `innerText` was not captured in this audit, so no specific production misclassification is claimed.
- One-second polling can traverse `body *` in the fallback parser. This is a performance risk on a large page, not a measured regression. Profile it, then consider scoped extraction and local visual ticking with periodic reconciliation.
- The controller owns many concerns, but a rewrite would add risk. Extract only a deterministic checkpoint policy and an independent report-draft owner as those features need them. Existing folder boundaries remain appropriate.
- CI currently runs version-script checks and a Debug build. Release builds/packages/verifies but does not run XCTest. Local `make release` does run tests. Put deterministic tests in a compatible hosted runner before treating remote CI as a reliability gate; verify runner OS/SDK availability rather than assuming the existing README's limitation remains current.

## Platform checks

All five bundled WAV files are 29.0-second, 16-bit files. They satisfy Apple's documented duration requirement; excess sound length was **not** found as the cause of inconsistency. They are still long for a gentle default reminder. [Apple notification sound requirements](https://developer.apple.com/documentation/usernotifications/unnotificationsound)

Apple documents that limited-space notification UI may display only the first two actions. The current five/six-action arrays are therefore poor places for an essential action at position three or later. This does not establish which actions every macOS presentation currently shows. [Apple category API](https://developer.apple.com/documentation/usernotifications/unnotificationcategory/init(identifier:actions:intentidentifiers:options:))
